# TransitScholar Layer2 Step2 Schema 提取与验证开发计划

**文档版本**：V1.0
**日期**：2026-08-14
**项目**：TransitScholar
**阶段**：Layer2 Step2（L2S2）
**定位**：面向深度强化学习公交调度 / 控制论文的可插拔、证据驱动 Schema 提取与验证层

---

## 1. Step2 定位与目标

TransitScholar 是一个面向大模型应用开发实习展示的 learning/demo 型 Deep Researcher Agent，首个重点领域是基于深度强化学习的公交调度与公交实时控制研究论文。

L2S2 的目标是：

> **基于 Layer2 Step1 已建立的 Canonical Paper Representation 与检索系统，将单篇论文转换为可比较、可追溯、可验证的结构化 Schema Instance。**

L2S2 不重新处理 PDF，也不重新实现 chunking、索引、embedding 或 rerank。所有论文内容访问统一依赖 L2S1 已冻结的 Canonical 与检索 API。

```text
Layer1
论文身份 / 主 PDF
        ↓
Layer2 Step1
Canonical Representation
+ grep / BM25 / Dense / Hybrid / Rerank
+ Evidence Retrieval
        ↓
Layer2 Step2
Schema Plugin
        ↓
Schema Extraction
        ↓
Validation
        ↓
Schema Instance
        ↓
后续 Wiki / Layer3 Agent
```

L2S2 的核心不是“让 LLM 总结论文”，而是：

> **按照一个显式的研究 Schema，对论文进行定向检索、提炼和证据绑定。**

---

## 2. 核心产品愿景

### 2.1 Schema 是可插拔研究视角

Schema 不应被硬编码成“公交 RL 专属数据结构”。

TransitScholar Core 应支持：

```text
Schema Extraction Engine
        +
Schema Plugin
```

V1 提供一个官方领域 Plugin：

```text
bus_control_rl
```

未来可继续扩展：

```text
llm_agent
computer_vision
medical_trial
economics
user_defined
...
```

同时允许：

```text
schema_enabled = false
```

此时 TransitScholar 仍然可以依赖 L2S1 与 Layer3 作为普通 Deep Researcher 工作。

因此：

> **公交 DRL 是首个高度优化的领域 Plugin，而不是 TransitScholar 的永久边界。**

### 2.2 Schema 的本质

Schema Field 不只是字段名，而是：

> **Research Question + Output Contract**

一个 Field 至少要表达：

- 要回答什么研究问题；
- 预期答案类型；
- 是否允许多个值；
- 是否允许推断；
- 是否必须提供证据；
- 找不到时如何表达；
- 合法枚举或结构约束。

示例：

```yaml
id: rl_formulation.rl_paradigm
label: RL Paradigm
description: The reinforcement learning paradigm used by the proposed method.
question: What reinforcement learning paradigm does the paper use?

type: enum
options:
  - SARL
  - MARL
  - Hierarchical RL
  - Other

evidence_required: true
allow_inference: true
```

## 3. L2S2 边界

L2S2 负责：

- Schema Plugin 定义；
- Schema Definition 加载与校验；
- 单篇论文 Schema Extraction；
- FieldResult 生成；
- Evidence 绑定；
- Structural Validation；
- Evidence Integrity Validation；
- Field Semantic Verification；
- Cross-field Consistency Validation；
- Targeted Recheck；
- Schema Instance 持久化、版本与 trace；
- 小规模真实论文 Schema 验收。

L2S2 不负责：

- PDF 解析；
- OCR / 扫描 PDF；
- 新的 chunking / embedding / rerank 体系；
- Wiki；
- Knowledge Graph；
- 跨论文推理；
- Layer3 Agent；
- Web 前端；
- 通用 ontology 系统；
- Schema Marketplace；
- 多模型投票；
- 多 Agent extraction；
- 自动训练 extraction 模型；
- 全量论文表格数值数据库。

---

## 4. Schema 不替代论文原始内容

Schema 是论文的一个**结构化研究视图**，不是论文的完整表示。

未来 Layer3 应遵循：

```text
优先查询 Schema
        ↓
Schema 不足
        ↓
回到 L2S1 Retrieval
```

不能让用户只能通过 Schema 访问论文。

原因是 Schema 天然存在“观察偏置”：它只主动抽取设计者提前认为重要的问题。

---

## 5. Schema Plugin 最小结构

V1 不建设复杂 Plugin Framework。

建议：

```text
schema_plugins/
└── bus_control_rl/
    ├── schema.yaml
    └── validators.py
```

其中：

- `schema.yaml`：定义要抽取什么；
- `validators.py`：定义领域专属 Cross-field consistency 规则。

未来如有明确需求，可增加：

```text
extraction_guidance.md
```

但 V1 优先把字段级 guidance 写入 `schema.yaml`，避免过度工程化。

---

## 6. Schema Definition 与 Schema Instance 分离

### 6.1 Schema Definition

回答：

> “我要从论文中抽取什么？”

例如：

```text
schemas/bus_control_rl/schema.yaml
```

### 6.2 Schema Instance

回答：

> “这篇论文对这些问题的答案是什么？”

例如：

```text
paper_001
→ bus_control_rl@1.0
→ schema_instance.json
```

Schema Definition 可以升级版本。

历史 Schema Instance 必须记录：

```text
schema_id
schema_version
schema_hash
```

---

## 7. Schema Definition 数据组织

Definition 层的 `sections` 与 `fields` 使用 List，以保证科研阅读和展示顺序。

```yaml
schema_id: bus_control_rl
version: "1.0"
name: Bus Control Reinforcement Learning Paper
description: ...

sections:
  - id: research_problem
    label: Research Problem
    fields:
      - ...

  - id: rl_formulation
    label: RL Formulation
    fields:
      - ...
```

Field Definition 至少支持：

```text
id
label
description
question
type
options / constraints
evidence_required
allow_inference
```

V1 类型系统：

```text
string
number
boolean
enum
list
object
```

不建设复杂 DSL。复杂字段通过 `list<object>` 或 `object` 表达。

---

## 8. Schema Instance 数据组织

Instance 使用：

```text
field_id → FieldResult
```

即 Hash Map。

```json
{
  "paper_id": "paper_001",
  "schema_id": "bus_control_rl",
  "schema_version": "1.0",
  "fields": {
    "rl_formulation.rl_paradigm": {
      "value": "MARL",
      "status": "explicit",
      "evidence": [],
      "confidence": 0.97,
      "notes": null
    }
  }
}
```

因此最终原则为：

> **Definition 用 List 保证组织顺序；Instance 用 Hash Map 保证访问便利。**

---

## 9. FieldResult 与 EvidenceRef

所有字段统一输出：

```json
{
  "value": "...",
  "status": "explicit",
  "evidence": [
    {
      "block_id": "blk_127",
      "char_start": 32,
      "char_end": 186,
      "pages": [6],
      "section_path": [
        "3 Method",
        "3.2 Reward Function"
      ],
      "quote": "..."
    }
  ],
  "confidence": 0.95,
  "notes": null
}
```

不再拆成“机器真值”和“展示信息”两套对象。EvidenceRef 本身就是完整证据对象。

要求：

> `block_id / char range / pages / section_path / quote` 必须从 L2S1 Canonical 或 RetrievalHit 回填、解析或校验，不能由 LLM 自由生成。

---

## 10. Field Status

V1 固定：

```text
explicit
inferred
unclear
not_found
not_applicable
conflicting
```

语义：

- `explicit`：论文明确说明；
- `inferred`：论文没有直接给出标签，但可由证据合理推断；
- `unclear`：存在相关内容，但无法稳定判断；
- `not_found`：正常检索和抽取完成，但没有找到足够证据；
- `not_applicable`：字段对当前论文不适用；
- `conflicting`：论文不同位置存在无法直接消解的冲突信息。

必须明确：

```text
not_found ≠ not_applicable
```

---

## 11. Confidence

保留：

```text
confidence ∈ [0,1]
```

其定位仅为模型自评辅助信息，不视为客观事实概率，也不依赖单一 confidence 阈值决定事实真伪。

真正的质量判断主要依赖：

```text
status
evidence
verifier
```

## 12. BusControlRL Schema V1 字段树

### 12.1 Research Problem

```text
research_problem
├── control_type
├── control_objective
├── network_scope
├── line_scope
└── problem_description
```

重点覆盖：

- holding；
- scheduling；
- speed control；
- stop skipping；
- mixed control；
- 单线路 / 多线路；
- 控制目标；
- 实际公交运营问题。

### 12.2 RL Formulation

```text
rl_formulation
├── rl_paradigm
├── algorithm
├── agent_definition
├── agent_granularity
├── centralized_or_decentralized
└── training_execution_paradigm
```

重点支持：

- SARL / MARL；
- TD3 / DDPG / SAC / PPO / DQN 等；
- 谁是 Agent；
- 一个 Agent 控制什么；
- centralized training / decentralized execution 等。

### 12.3 Decision Model

```text
decision_model
├── state
├── action
├── reward
├── decision_timing
├── decision_interval
└── action_constraints
```

`state / action / reward` 应优先使用结构化列表或 object，而不是长字符串。

例如：

```json
[
  {
    "name": "forward_headway",
    "description": "..."
  },
  {
    "name": "passenger_load",
    "description": "..."
  }
]
```

### 12.4 Control Constraints

```text
control_constraints
├── holding_upper_bound
├── holding_lower_bound
├── holding_location
├── operational_constraints
└── other_constraints
```

必须支持 `not_found` 与 `not_applicable` 的区别。

### 12.5 Baselines

Baselines 使用结构化列表：

```json
[
  {
    "name": "SNC",
    "category": "conventional_control",
    "description": "..."
  },
  {
    "name": "DDPG",
    "category": "reinforcement_learning",
    "description": "..."
  }
]
```

至少支持：

```text
No Control
传统控制方法
优化方法
RL baseline
作者方法变体
```

V1 不建设复杂 baseline ontology。

### 12.6 Experimental Setup

```text
experimental_setup
├── simulator
├── route_or_network
├── demand_setting
├── scenario_setting
├── training_setting
├── random_seed
└── evaluation_protocol
```

重点服务未来论文可比性分析。

### 12.7 Metrics

Metrics 使用结构化列表：

```json
[
  {
    "name": "waiting_time",
    "description": "...",
    "unit": "s"
  },
  {
    "name": "headway_cv",
    "description": "...",
    "unit": null
  }
]
```

重点包括但不限于：

```text
waiting time
holding time
travel time
headway
headway CV
bunching-related indicators
reward / return
```

不强制映射成有限枚举。

### 12.8 Results

```text
results
├── main_results
├── baseline_comparisons
├── ablation_results
└── main_conclusions
```

V1 不追求完整数据库化所有数表。重点是：

> 提取作者最重要的实验结论，并绑定 evidence。

复杂统计与 CSV 分析留给后续 Python / experiment-analysis tools。

### 12.9 Comparability

```text
comparability
├── comparable_dimensions
├── important_differences
├── comparison_caveats
└── comparability_summary
```

记录影响未来跨论文比较的因素，例如：

```text
单线 / 多线
SARL / MARL
不同 demand
不同 holding upper bound
不同 simulator
不同 state information
不同 baseline
不同评价指标
```

L2S2 只准备结构化条件，真正 cross-paper reasoning 留给后续 Wiki / Layer3。

## 13. Extraction Engine

L2S2 Extractor 不直接阅读全文。

每个 Field 或 Field Group 的基本流程：

```text
Field Definition
        ↓
生成 retrieval query / queries
        ↓
调用 L2S1 Retrieval
        ↓
候选 Evidence
        ↓
LLM 提炼
        ↓
FieldResult
```

主检索路线默认：

```text
search_hybrid()
```

必要时允许补充：

```text
grep_paper()
search_bm25()
read_context()
read_section()
```

V1 不做复杂 ReAct Agent。

---

## 14. Field-oriented Extraction

不推荐：

```text
整篇论文所有 chunks
        ↓
一个超大 Prompt
        ↓
一次性输出完整 Schema
```

推荐：

```text
Schema Section
      ↓
Field / Field Group
      ↓
定向 Retrieval
      ↓
Extraction
```

优点：

- evidence 更容易绑定；
- 上下文更干净；
- 字段失败可以局部重试；
- 更适合用户自定义 Schema；
- 更容易验证和定位错误。

但不机械坚持“一 Field 一 API 调用”。

允许将高度相关字段组成 Extraction Group，例如：

```text
state + action + reward
algorithm + rl_paradigm + agent_definition
metrics + main_results
```

具体 batching 属于实现优化，不进入 Schema 语义层。

---

## 15. LLM 输出边界

LLM 只负责：

```text
value
status
选择 evidence candidate IDs
confidence
notes
```

不允许 LLM 自己创造：

```text
block_id
page
bbox
section
char_start / char_end
```

建议将 Retrieval 候选 Evidence 映射为：

```text
E1
E2
E3
...
```

LLM 输出：

```json
{
  "value": "MARL",
  "status": "inferred",
  "evidence_ids": ["E1", "E3"],
  "confidence": 0.86
}
```

程序层再根据 `evidence_ids` 回填真正的 EvidenceRef，从结构上防止 hallucinated citation。

## 16. 统一 LLM 设计

### 16.1 V1 只配置一个统一 LLM

L2S2 的：

- Extractor；
- Semantic Verifier；
- Targeted Recheck；

全部使用**同一个配置、同一个模型**。

它们是不同调用阶段和 Prompt 角色，不是不同模型。

```text
                   L2S2
                     │
              Unified LLM Client
                     │
         同一个配置、同一个模型
            /         |                    ↓          ↓          ↓
      Extractor    Verifier    Recheck
```

V1 不实现：

```text
多模型路由
Verifier 专用模型
模型投票
角色独立 Provider
```

### 16.2 Unified LLM Client

Provider 层不应知道 `extract / verify / recheck` 这些业务语义。

统一接口只负责：

> 给定 messages 与 structured output schema，调用一次 LLM。

概念接口：

```python
class LLMClient:
    def generate_structured(
        self,
        messages,
        output_schema
    ):
        ...
```

上层模块统一调用该 Client。

### 16.3 LLM Provider 与 API Key 边界

L2S2 的真实抽取、语义验证和 targeted recheck 需要 LLM，但默认自动化测试不得依赖真实网络或真实 API。

V1 必须同时提供两类 provider：

```text
fake
真实 LLM provider
```

其中：

- `fake` provider 用于 deterministic tests 与 fake-LLM end-to-end tests；
- 真实 provider 只用于手动验收、真实论文 benchmark 或用户明确授权的运行；
- provider 不得在日志、manifest、trace、错误信息中写入 API key 明文；
- 若 API key 未配置、网络不可用、provider 超时或 structured output 无效，必须返回明确的 `unavailable` / `extraction_failed` / `validation_failed`，不得伪装成 `not_found`。

API key 读取必须沿用项目已有 `.env` / `config.py` 边界，新增环境变量建议使用：

```text
TRANSIT_SCHOLAR_LLM_PROVIDER=
TRANSIT_SCHOLAR_LLM_MODEL=
TRANSIT_SCHOLAR_LLM_API_KEY=
TRANSIT_SCHOLAR_LLM_BASE_URL=
TRANSIT_SCHOLAR_LLM_ALLOW_NETWORK=
```

默认值建议：

```text
TRANSIT_SCHOLAR_LLM_PROVIDER=fake
TRANSIT_SCHOLAR_LLM_ALLOW_NETWORK=false
```

只有当用户显式设置 `TRANSIT_SCHOLAR_LLM_ALLOW_NETWORK=true` 且配置了真实 provider/key 时，真实 LLM 调用才允许发生。

### 16.4 Structured Output 失败边界

LLM structured output 必须由程序层校验。

失败场景包括：

```text
非 JSON
JSON schema 不匹配
缺少 required 字段
evidence_ids 指向不存在的候选证据
status / confidence / value 类型不合法
```

这些失败属于 extraction 或 verification 失败，不属于论文中“没有找到信息”。

程序不得让 LLM 重新生成 `block_id / char_start / char_end / pages / section_path / quote`。这些证据字段只能从 L2S1 Canonical 或 RetrievalHit 回填。

## 17. Validation 总体设计

L2S2 建立四层 Validation：

```text
① Structural Validation
② Evidence Integrity Validation
③ Field Semantic Verification
④ Cross-field Consistency Validation
```

四层职责必须分离。

---

## 18. 第一层：Structural Validation

纯程序完成。

检查：

```text
Schema Definition 是否合法
FieldResult 格式
value 类型
enum 合法性
list/object 结构
status 合法性
confidence 范围
evidence_required
必填字段
```

推荐使用 Pydantic。

不使用 LLM。

---

## 19. 第二层：Evidence Integrity Validation

目标：

> 确保每一个 EvidenceRef 都真实存在于 L2S1 Canonical。

检查：

```text
paper_id 是否一致
block_id 是否存在
char_start / char_end 是否有效
quote 是否与 Canonical 对应 substring 一致
pages 是否来自 provenance
section_path 是否正确
```

这一层完全确定性，不使用 LLM。

---

## 20. 第三层：Field Semantic Verification

Verifier 输入：

```text
Field Question
+
Extracted Value
+
Status
+
全部 Evidence
```

判断：

> 这些 Evidence 作为一个整体，是否足以支持当前 Value？

不是逐 Evidence 做独立筛选。

输出：

```text
supported
partially_supported
unsupported
conflicting
```

例如：

```json
{
  "verdict": "supported",
  "reason": "...",
  "confidence": 0.94
}
```

关键原则：

> **Verifier 检查整个 Evidence Set 对 Value 的整体支撑关系。**

只要整体支撑，Extraction 阶段选中的 Evidence 全部保留。Verifier 不负责 evidence pruning。

### 特殊规则

- `explicit`：Evidence Set 应直接支持 Value；
- `inferred`：Evidence 不必直接出现标签，但整体必须足以支持推断；
- `not_found`：不能因为 evidence 为空就证明全文绝对不存在，其可信度来自正常 Retrieval + Extraction；
- `conflicting`：Verifier 判断 Evidence Set 内部是否存在无法消解的事实冲突。

---

## 21. 第四层：Cross-field Consistency Validation

目标：

> 单字段成立以后，检查整份 Schema 内字段之间是否存在异常关系。

主要分四类。

### 21.1 Field Dependency

例如：

```text
control_type = holding
```

通常应与：

```text
holding action
holding upper bound
holding location
```

存在合理关系。

若：

```text
control_type = pure scheduling
holding_upper_bound = explicit 60s
```

不直接判错，而生成 warning，提示复核 `control_type` 是否应为 mixed。

### 21.2 Semantic Consistency

例如：

```text
rl_paradigm = SARL
agent_definition = multiple independently acting buses
```

应触发复核。

又如：

```text
algorithm = DQN
action = continuous holding duration
```

如果没有抽取到 action discretization，也应产生 warning。

Cross-field validator 发现的是“不协调”，不是直接判论文或 Schema 一定错误。

### 21.3 Numerical Consistency

例如：

```text
action.range = [0, 60] seconds
holding_upper_bound = 90 seconds
```

应触发 warning。

未来还可检查：

```text
baseline value
proposed value
reported improvement
```

之间的简单数值一致性。

V1 只实现明显且稳定的规则。

### 21.4 Relational Completeness

例如：

```text
main_results 中出现 PPO
```

但：

```text
baselines 中没有 PPO
```

可能说明 baseline extraction 漏召回。

又如：

```text
main_results 中出现 holding_time
```

但：

```text
metrics 中没有 holding_time
```

应触发相关字段 recheck。

---

## 22. Cross-field Validator 行为边界

Cross-field validator：

```text
只发现问题
不直接修改 Schema
```

输出：

```json
{
  "type": "cross_field_consistency",
  "severity": "warning",
  "fields": [
    "rl_formulation.rl_paradigm",
    "rl_formulation.agent_definition"
  ],
  "message": "...",
  "action": "recheck"
}
```

禁止：

```text
发现 SARL / MARL 冲突
→ 自动把 SARL 改成 MARL
```

## 23. Plugin 与 Core 的 Validator 边界

通用 Core 负责：

```text
Structural Validator
Evidence Integrity Validator
Semantic Verifier
```

BusControlRL Plugin 负责：

```text
Cross-field Validators
```

因为 TransitScholar Core 不应硬编码：

```text

MARL
holding
headway
DQN
```

之间的领域知识。

## 24. Targeted Recheck

如果 Verifier 或 Cross-field Validator 发现问题：

```text
只重新处理相关字段
```

流程：

```text
Initial Extraction
       ↓
Validation
       ↓
发现问题？
 ┌─────┴─────┐
 No          Yes
 ↓            ↓
Accept    Targeted Retrieval
             ↓
         Re-extraction
             ↓
         Re-validation
```

V1 约束：

> 每个 Field 最多自动 recheck 一次。

仍无法解决时，允许如实保留：

```text
unclear
conflicting
```

避免无限循环。

## 30. Observability / Trace

每个 Field 至少记录：

```text
retrieval queries
retrieved chunk ids
candidate evidence ids
selected evidence ids
extraction result
verification result
是否发生 recheck
最终状态
```

这些 trace 放入 extraction manifest / run trace，不需要全部塞进最终 Schema Instance。

目标是以后能够定位：

```text
为什么 reward 抽错？
```

究竟是：

```text

Verifier 放过
Cross-field 没发现
```

## 31. Error Handling

系统失败不能伪造成：

```text
not_found
```

例如：

```text
Jina unavailable
LLM API failure
Schema Definition invalid
Retrieval unavailable
Evidence integrity failure
```

必须返回明确失败状态，例如：

```text
extraction failed
unavailable
validation failed
```

`not_found` 只表示：

> 正常检索和抽取完成，但没有找到足够证据。

## 32. 依赖与配置决策

L2S2 不应隐式依赖其他包的传递依赖。开发时需要显式确认并写入 `pyproject.toml`：

```text
pydantic
pyyaml
```

理由：

- `pydantic` 用于 Schema Definition、FieldResult、EvidenceRef、SchemaInstance 与 ValidationIssue 的结构校验；
- `pyyaml` 用于读取 `schema.yaml`；
- 真实 LLM provider 如果通过 HTTP 调用，应优先复用项目已有 `httpx` 依赖；若当前安装组无法保证可用，应明确放入对应 dependency group。

依赖边界：

- deterministic tests 与 fake-LLM tests 不得依赖真实 LLM API、Jina、Docling、LanceDB 或其他网络服务；
- L2S2 不新增 PDF parser、embedding、reranker 或 OCR 依赖；
- L2S2 不把 Schema Instance 写入 SQL 数据库，主存储仍为 JSON 派生产物。

## 34. 推荐验收指标

### 34.1 Field Value Accuracy

判断字段值是否正确。

对 list/object 字段可人工分为：

```text
correct
partially_correct
incorrect
```

V1 不建设复杂 ontology-based F1。

### 34.2 Status Accuracy

检查：

```text
explicit
inferred
unclear
not_found
not_applicable
conflicting
```

判断是否合理。

### 34.3 Evidence Support Rate

核心指标：

> Field Value 是否被其 Evidence Set 整体充分支持。

人工判断：

```text
supported
partially_supported
unsupported
conflicting
```

### 34.4 Evidence Traceability Rate

要求：

> 所有非空 Evidence 都能严格回溯 L2S1 Canonical。

这是确定性工程指标，目标应接近 100%。

### 34.5 Not-found Correctness

专门检查系统没有找到时是否会脑补。

## 35. V1 Acceptance 原则

不人为追求过高 benchmark 数字。

V1 重点证明：

1. Schema Engine 能稳定运行；
2. BusControlRL Plugin 符合真实公交 DRL 论文阅读习惯；
3. Schema Plugin 可替换；
4. Schema 可关闭；
5. 所有非空事实有 Evidence；
6. hallucinated evidence 被结构性禁止；
7. Verifier 能识别明显 unsupported claim；
8. Cross-field validator 能发现典型不一致；
9. Targeted recheck 能局部修复；
10. 错误可定位到 retrieval / extraction / verification 环节；
11. 真实论文核心字段整体达到可用质量。

其中，Deterministic Tests 与 Fake-LLM End-to-end Tests 是工程闭环验收；Real-paper Schema Benchmark 是 L2S2 正式冻结前的质量验收。前者通过后可以认为 L2S2 主链路 feature complete，后者通过后才建议进入正式 freeze。

## 36. 推荐开发包

L2S2 不建议严格拆成 11 个细 Phase 串行开发。原有能力点应保留，但实际施工应合并为 4 个工程开发包 + 1 个冻结验收包。

这样做的原因是：

- Schema core、plugin definition 与 custom schema proof 都属于定义层，拆开会导致过早假定 core 只服务 `bus_control_rl`；
- LLM client、retrieval、evidence candidate、FieldResult 与初版 instance 必须一起跑通，单独开发 LLM client 只会形成空壳；
- Structural validation、evidence validation、semantic verifier、cross-field validator 与 targeted recheck 都服务同一条质量闭环，过细拆分会增加返工；
- persistence、versioning、trace 与 public API 是后续 Layer3 的稳定边界，应集中验收；
- real-paper benchmark 是冻结前质量验收，不应阻塞前面工程闭环。

### Package A — Schema Core + Plugin Definition

合并原 Phase 1、Phase 2 与 Phase 10 的定义层内容。

实现：

```text
SchemaDefinition
SectionDefinition
FieldDefinition
FieldResult
EvidenceRef
SchemaInstance
ValidationIssue
Plugin interface
Plugin loader
schema hash / version
bus_control_rl/schema.yaml
bus_control_rl/validators.py 的规则入口
generic_research_paper 最小 custom schema proof
```

验收重点：

- Pydantic models、serialization 与 schema hash/version 稳定；
- `bus_control_rl` 字段树符合本文档第 12 节；
- `generic_research_paper` 证明仅新增合法 Schema Definition 即可接入；
- core 不硬编码公交 DRL 字段或枚举；
- structural validation 能发现非法 definition、非法 field type、非法 status、非法 enum 选项。

### Package B — Extraction Engine + Fake LLM E2E

合并原 Phase 3、Phase 4 与 Phase 9 的初版 instance / trace 内容。

实现：

```text
Unified LLM Client
fake provider
真实 provider 配置边界
Field / Field Group retrieval query
Candidate Evidence E1/E2/E3 映射
LLM structured extraction
evidence_ids → EvidenceRef 回填
FieldResult
SchemaInstance
初版 extraction_manifest / run trace
```

验收重点：

- 默认测试走 fake provider，不依赖真实 API；
- LLM 只输出 `value / status / evidence_ids / confidence / notes`；
- `block_id / char_start / char_end / pages / section_path / quote` 只能由程序从 L2S1 Canonical 或 RetrievalHit 回填；
- invalid structured output 返回明确失败，不伪装成 `not_found`；
- fake-LLM end-to-end 能覆盖 retrieval → extraction → evidence binding → Schema Instance。

### Package C — Validation + Recheck

合并原 Phase 5、Phase 6、Phase 7 与 Phase 8。

实现：

```text
Structural Validation
Evidence Integrity Validation
Semantic Verifier
BusControlRL Cross-field Validation
Targeted Recheck
validation_report
recheck trace
```

验收重点：

- Structural validation 校验 FieldResult 格式、value 类型、status、confidence、evidence_required；
- Evidence integrity validation 校验 block 存在、char range 有效、quote 与 canonical substring 一致、pages 与 section_path 可回溯；
- Semantic verifier 判断 evidence set 对 value 的整体支撑关系；
- cross-field validator 只产生 warning / issue，不直接修改 schema field；
- targeted recheck 每个 field 最多自动执行一次，失败后保留 `unclear` / `conflicting` / 明确失败状态；
- system failure 不得伪装成 `not_found`。

### Package D — Persistence / Versioning / Public API

合并原 Phase 9 的剩余持久化内容与第 28 节 Public API。

实现：

```text
data/layer2/schemas/<paper_id>/current.json
data/layer2/schemas/<paper_id>/runs/<schema_run_id>/schema_instance.json
data/layer2/schemas/<paper_id>/runs/<schema_run_id>/extraction_manifest.json
data/layer2/schemas/<paper_id>/runs/<schema_run_id>/validation_report.json
schema run versioning
schema rebuild rules
list_schema_plugins()
get_schema_definition(schema_id)
extract_schema(paper_id, schema_id="bus_control_rl")
get_schema(paper_id, schema_id="bus_control_rl")
get_field(paper_id, schema_id, field_id)
validate_schema(paper_id, schema_id)
recheck_fields(paper_id, schema_id, field_ids)
```

验收重点：

- 后续 Layer3 不依赖内部目录结构，只依赖 public API；
- schema definition hash、LLM model、prompt version、source parse run 与 retrieval manifest 变化能产生可追溯的新 schema run；
- current 指针只指向完整写入且可读取的 run；
- trace 足以定位错误来自 retrieval、extraction、verification、cross-field 还是 recheck。

### Package E — Real-paper Acceptance

对应原 Phase 11，定位为**冻结前验收包**。

选择 5～10 篇公交 DRL 论文，人工建立每篇 10～15 个核心字段 gold，完成：

```text
Field Accuracy
Status Accuracy
Evidence Support
Evidence Traceability
Not-found Correctness
Failure Analysis
```

验收重点：

- 真实论文核心字段整体达到用户认可的可用质量；
- 所有非空事实有 evidence，且 evidence traceability 接近 100%；
- 对 list/object 字段允许人工标为 `correct / partially_correct / incorrect`；
- 不人为追求过高 benchmark 数字；
- 若 Package A～D 已通过 deterministic 与 fake-LLM end-to-end 测试，可以先宣告 L2S2 工程主链路 feature complete；只有 Package E 通过后，才宣告 L2S2 V1 正式冻结。
