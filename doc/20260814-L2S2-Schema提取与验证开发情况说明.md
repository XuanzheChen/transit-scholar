## 1. 总体状态

L2S2 的目标是基于 L2S1 的 Canonical Paper Representation 与检索系统，把单篇论文转换为可比较、可追溯、可验证的结构化 Schema Instance。

截至当前，5 个开发包状态如下：

| Package | 计划定位 | 当前状态 |
|---|---|---|
| Package A | Schema Core + Plugin Definition | 已完成，通过 E 验收 |
| Package B | Extraction Engine + Fake LLM E2E | 已完成，通过 E 验收 |
| Package C | Validation + Recheck | 已完成，通过 E 验收 |
| Package D | Persistence / Versioning / Public API | 已完成，通过 E 验收 |
| Package E | Real-paper Acceptance | 已完成，通过 E 验收；提供验收框架、模板、指标、报告与 CLI |

当前可以宣告的是：

- Schema 定义层、插件层、抽取引擎、证据绑定、验证链路、recheck、持久化、公开 API、真实论文验收框架均已落地。
- 离线 deterministic 测试闭环已完成。
- Package E 已提供真实论文验收所需的 gold 格式、模板、评估指标和报告工具。
- 真实论文正式 gold 已完成并经用户审核认可，文件为 `tests/fixtures/l2s2_schema_acceptance/codex_reviewed_gold.json`。
- 2026-08-21 用户已明确宣告 L2S2 V1 正式 Freeze。

当前仍需保留的边界是：

- 不能宣告所有字段与 gold 的 acceptable_values 逐字一致；当前仍有 85 条 warning 诊断。
- 不能宣告工具自动完成冻结；历史报告中的 `declared_frozen=false` 是生成时事实，正式 Freeze
  来自 2026-08-21 用户治理宣告，而不是工具自行改写历史报告。

当前可以补充宣告：正式 Gold 的真实链路验收已经达到 `freeze_suggestion=ready`，blocking error 为 0，
Package E 已达到 acceptance-ready 状态，structured-output 真实 smoke 已通过，且 L2S2 V1 已正式
Freeze；具体指标、非阻断风险与 Freeze 基线见第 14、17、18 节。

真实 LLM provider 边界已实现（见第 12 节）：`OpenAICompatibleLLMClient` 已可实际调用，但真实网络请求仍需用户显式 `ALLOW_NETWORK=1` + key/base_url/model 授权。
`task-2026-08-20-001`（见第 15 节）进一步把正常 runtime 接到统一配置：默认 `extract_schema()` 不再硬编码 fake，
而是通过 `.env -> LLMConfig.from_env() -> resolve_runtime_llm_client()` 解析真实 client，并由公开 API 组合根

`provider=fake`、显式注入的 fake 和 deterministic 测试。配置缺失或联网禁止时默认 runtime 显式失败
（`LLMUnavailableError`），绝不静默 fallback fake。

> 更新（task-2026-08-15-001）：真实 OpenAI-compatible provider 已在本任务中补齐，
> 见第 12 节。以下为本任务之前的原始记录，保留作为历史说明。

本任务之前，`src/transit_scholar/layer2/schema_extraction/llm.py` 只实现统一配置边界和 `FakeLLMProvider`，真实 provider 是 `RealLLMClientStub`：

```text

```

这意味着系统当时已经具备“真实 provider 配置边界”和“禁止默认联网”的安全行为，但还不能实际调用真实 LLM 完成真实 Schema 抽取。

判断（历史口径）：

- 如果把计划中的“真实 provider”理解为“必须真的能请求模型 API”，则当时未达预期。

## 15. 真实 LLM Runtime Wiring（task-2026-08-20-001）

本任务（`tasks/task-2026-08-20-001`）按冻结验收 `acceptance.md`（AC-RW-01..20）修复 L2S2 的

### 15.1 统一 dotenv 边界（FR-001 / AC-RW-01..03）

- 根 `.env` 只能由 `transit_scholar.config._load_project_dotenv()` 统一加载（`override=False`）；
  新增一次性守卫 `ensure_project_dotenv()`（进程内只加载一次）与可派生的 `project_dotenv_path()`；
  `schema_extraction` 子模块不自行调用 `load_dotenv()`、不读写 `.env`。
- `LLMConfig.from_env()` 保持纯 `os.environ` 读取；正常 runtime 的 `resolve_runtime_llm_client()`
  先懒加载调用 `ensure_project_dotenv()`，再读取 env，从而“复用 bootstrap 即可让 from_env 读到根 `.env`”。

### 15.2 Runtime LLM resolver（FR-002 / AC-RW-04..06）

- 冻结真值表：显式 `provider=fake` -> `FakeLLMProvider`；provider 缺失/空白 -> 显式
  `LLMUnavailableError`（绝不 fake、绝不 `not_found`）；`openai_compatible` 且
  model/key/base_url/`ALLOW_NETWORK=1` 完整 -> `OpenAICompatibleLLMClient`；其他 provider ->
  `RealLLMClientStub`（调用即抛）；配置缺失 / 联网禁止 / 初始化失败 -> 显式错误。
- `resolve_runtime_llm_client()` 额外受 `TRANSIT_SCHOLAR_BLOCK_NETWORK` 门禁：联网阻断时真实 provider
  在任何 client 构造之前抛 `LLMUnavailableError`；显式 fake 免疫（本就离线）。
- 未注入 `llm_client` 的 `extract_schema()`（以及未注入 client 的 engine）默认走
  `LLMConfig.from_env() -> resolve_runtime_llm_client()`，不再固定构造 `FakeLLMProvider`。
- 显式注入 `FakeLLMProvider` / custom client 始终优先，真实 `.env` 不覆盖注入 client，resolver 不被调用。

## 17. Structured Output Reliability Contract（task-2026-08-21-001）

### 17.1 根因与最终契约

2026-08-20 的真实 verifier smoke 失败，根因不是 Fake/runtime wiring：请求已经使用正常
runtime 解析出的真实 shared client，并进入了 `StructuredSemanticVerifier`。根因是 provider
请求固定为 `response_format={"type":"json_object"}`，调用方传入的 Pydantic
`output_schema` 没有作为 strict JSON Schema 下推，而且 shared client 缺少统一、有限的
structured correction；因此 provider 返回 `{}` 时虽是合法 JSON，却不满足
`SemanticVerdict.decision` 的必填契约。

`task-2026-08-21-001` 将可靠性边界修正为：

- 调用方传入的 Pydantic `output_schema` 是 provider constraint、JSON-object guidance、
  correction guidance 与最终程序校验的唯一结构来源；Extractor、Verifier、Recheck 的业务
  prompt 不再维护第二套手写输出字段契约。
- 新增 `TRANSIT_SCHOLAR_LLM_STRUCTURED_OUTPUT_MODE=auto|json_schema|json_object`，默认
  `auto`；非法值在 client 构造/发网前失败。
- `json_schema` 发送稳定 schema name、`strict=true` 与
  `output_schema.model_json_schema()`；`json_object` 只发送 JSON-object response format，并从
  同一 Pydantic schema 生成 prompt guidance。
- `auto` 先发送 strict schema，只在 provider 的结构化 error envelope 明确指出
  `response_format/json_schema` 不受支持时 fallback 一次。401、403、429、timeout、connection、
  普通 4xx、5xx 或仅含泛化 “schema/JSON” 文本的错误不触发 capability fallback。
- 每个 HTTP 200 内容仍依次经过 response envelope、JSON parse、object type 与
  `output_schema.model_validate()`。首次 structured 内容无效时，shared client 最多追加一次同
  client/model/mode 的 correction；上下文仅包含脱敏、限长的前次无效输出和校验信息。第二次
  仍无效显式抛 `LLMInvalidOutputError`，不猜测 `unclear`、不填默认字段、不 fake-success、
  不转换成 `not_found`。
- transport retry、capability fallback、structured correction 分别有独立上界。real shared
  client 已耗尽 format correction 后，Extractor 不再重复同质 format retry；evidence id、字段
  业务类型、absent-status 等后置业务纠错仍保留。
- composition root 的对象身份与注入优先级不变：Extractor、`StructuredSemanticVerifier`、
  Targeted Recheck 继续复用同一个 `StructuredLLMClient`；Verifier/Recheck 不重新加载 `.env`、
  不构造第二 provider、不复制 parser/correction。

### 17.2 真正的单字段 smoke 与当前证据状态

`scripts/l2s2_runtime_smoke.py` 现在强制且只接受一个 `--paper` 与一个 `--field`。它先从现有
`bus_control_rl` definition 确认 field，然后使用真实 `HybridRetrievalWrapper`，只对该 field
执行 extraction，再把同一个 runtime-resolved client 交给 `StructuredSemanticVerifier`。它不
修改或合成 Schema/Gold，不持久化完整 Schema run，不访问其他 38 个字段，也不触发 full-schema
validation/recheck。成功输出只包含 provider、可公开 model、client class、有效网络许可、paper、
field、extraction status、semantic decision 与 `final_success=true`；capability failure、HTTP 200
invalid output 和其他 runtime failure 分开报告，且不输出 key、Authorization/Bearer value 或完整
base URL。

实施后的受控进程没有修改 `.env`，而是在进程级设置
`TRANSIT_SCHOLAR_BLOCK_NETWORK=0`、`TRANSIT_SCHOLAR_RETRIEVAL_ALLOW_NETWORK=true`，并复用
现有隔离 L2S1 data root。运行时安全解析结果为：

```text

allow_network=True
block_network=False
```

真正的 `transit-001 / research_problem.control_type` 一篇论文 × 一个字段 smoke 最终以 exit code 0

```text

```
